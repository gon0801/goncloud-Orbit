## Qué hace el trabajo

`primer-ciclo.sh` corre `primer-ciclo.sql` con `psql` dentro de `orbit-db-1`. El `.sql` abre
`BEGIN READ ONLY` y cierra con `ROLLBACK`, así que no puede escribir. Mira solo los ciclos terminados
que **empezaron después** de la primera config que dejó las cuatro claves en `live` (la 59, buscada por
sus claves y no por su número) y responde a los cinco casos de paro del plan. Cuando todavía no hay
ningún ciclo terminado, la sección (2) lo dice con esas palabras. El resultado se manda por Telegram
con `envia_recordatorio.py`, y la última línea del mensaje es el veredicto: `SIN CASOS DE PARO` o
`CASO DE PARO: revisar la seccion (8)`.

Se ejecutó una vez a mano para probar el camino completo (2026-11-22 17:01 UTC): salió
`SIN CASOS DE PARO`, con el aviso de que todavía no hay ningún ciclo terminado después del encendido,
y `envios.log` registró `enviado: True`.

## La sonda detecta lo que debe detectar

Como en producción todavía no hay ninguna entrada ni ningún regreso, las dos comparaciones del `.sql`
se probaron con valores conocidos, por la misma entrada de solo lectura:

```
select 'baja 8.00 -> 5.59 (mas de 30%)' as caso,
       count(*) filter (where n < a * (1 - 30::numeric / 100)) as paro
  from (values (8.00::numeric, 5.59::numeric)) v(a, n)
union all
select 'baja 8.00 -> 5.60 (exacto 30%)', count(*) filter (where n < a * (1 - 30::numeric / 100))
  from (values (8.00::numeric, 5.60::numeric)) v(a, n)
union all
select 'regreso 5.60 -> 5.59 (baja)', count(*) filter (where n < a)
  from (values (5.60::numeric, 5.59::numeric)) v(a, n)
union all
select 'regreso 5.60 -> 6.40 (sube)', count(*) filter (where n < a)
  from (values (5.60::numeric, 6.40::numeric)) v(a, n)
```

```
baja 8.00 -> 5.59 (mas de 30%)|1
baja 8.00 -> 5.60 (exacto 30%)|0
regreso 5.60 -> 5.59 (baja)|1
regreso 5.60 -> 6.40 (sube)|0
```

El borde exacto del 30 % no dispara (5.60 es la reducción legítima de 8.00) y un centavo más abajo sí.
El regreso que sube no dispara y el que baja sí.
